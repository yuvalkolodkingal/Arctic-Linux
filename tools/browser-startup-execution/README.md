workflow, acquire an image, change product code or establish qualification.

The execution checkout and image-source checkout are siblings. Both are clean,
the latter is exactly SourceA326, and every invoked source helper is checked
against tracked bytes and its manifest hash. All five original observer files
retain their frozen bytes. No browser flags, renderer override, service changes,

The VM conditions match SourceA326's actual paired workload: UEFI, q35,
`-cpu max`, **two vCPUs**, **4096 MiB**, KVM, default virtio VGA, normal installed
boot with `--boot-append ''`, console authentication followed by restoration to
the real Wayland VT, the same candidate `profiles/ci/offline.toml`, and restricted

One new offline installation produces a clean powered-off disk and firmware
store. One fresh overlay of that new disk runs the diagnostic; it is never a
benchmark disk, snapshot, host or boot. The untouched install base, toolchain,
input ISO and image-source checkout are rechecked afterwards.

The frozen observer opens the same direct `epiphany --new-window` loopback
workload, holds its first window for **45 seconds**, then makes **three** repeated
launches with five-second persistence checks. This is existing workload
preconditioning, not an extra browser preloading policy. RPM verification and
whole ELF hashing can warm storage, and uprobes add cost. These diagnostic
intervals cannot replace paired performance acceptance or prove an optimization.
The full paired observer also executes other roles and settle/idle/shell work
before warmed browser launches. This browser-only diagnostic omits that prior
sequence and does not reproduce the complete paired cache state.
The original six-boot baseline diagnostic remains a separate source-closed
reference; this candidate phase run does not reacquire or rerun that baseline.

The host composer embeds actual pinned collector/helper bytes and a context
derived from the original disabled observer context. The guest validates every
size/hash before staging. It covers only the immutable diagnostic data CD's
`/run/t` mount with a root-owned **0700**, `nosuid,nodev,noexec` tmpfs, writes four
regular **0600** root-owned files without following symlinks, rechecks bytes,
runs the unchanged collector and unmounts this layer before returning to the
original harness. The CD and installed configuration are unchanged. This is
explicit RAM staging, not a claim that the original CD files are root owned.

Raw UART, app output, ordinary harness diagnostics, screenshots and disks remain
under the new private **0700** hosted task directory. Only one bounded report
envelope with sequential base64 pieces and an exact byte count/SHA can be
extracted. It must bind the actual final image, collector, helpers, execution,
staged file modes and actual Mango whole-ELF hash. The host uploads only this
finite JSON report and typed host receipt after the unchanged original-preserving
privacy scanner passes. There is no `always()` raw-log upload or exception text
echo. Failed collection emits a fixed status and retains private originals.
The task owns and verifies removal of its containers and labeled immutable VM
tools image, including acquisition/cancellation failures. GitHub hosted task
teardown ends the disposable VM/disk scope; no instrumented disk is reused.

Official Epiphany 50.6 source bytes are retained by the observer preparation.
The initial GLib 2.88.0 header argument-order reference lacks retained original
header bytes/hash. Exact Fedora GLib 2.88.3 runtime ABI and tracefs execution have
not been measured. That limit is explicit; this preparation adds no acquisition
