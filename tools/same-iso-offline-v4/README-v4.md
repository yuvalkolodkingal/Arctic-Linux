## Actual diagnosis and limits

The actual arctic-offline job in run 37520174911 failed after an observed LUKS prompt and a QMP BrokenPipe at approximately 36 seconds when the normal-desktop harness attempted login. Its after-update serial is only 380 bytes of OVMF output; QEMU exit status, guest QMP shutdown cause, completed history and actual transaction success were not captured. The earlier installed first pass has 43 passed records, one explicitly unrun Nix version-change record, and successful signed staging of 73 packages. The tail's powerdown text is replayed **serial-install.log from the earlier live install**, not update-cycle proof. `diagnosis-v4.json` pins these actual files and the exact source evidence.

Candidate DNF5 5.4.6.0 runs the stored offline transaction through `dnf5-offline-transaction.service` under system-update.target, then requests a guest reboot after success, or poweroff when stored `poweroff_after` is true. Arctic's `arm_text` changes only the state to ready and retains other fields. [Exact DNF5 source](https://github.com/rpm-software-management/dnf5/blob/5.4.6.0/dnf5/commands/offline/offline.cpp) and the captured same-version Fedora service units support a separate update cycle before the normal desktop boot. [QEMU documentation](https://www.qemu.org/docs/master/system/invocation.html) defines `-no-reboot` as exiting rather than rebooting. This explains a plausible harness phase mismatch; it does not establish that the actual failed transaction completed or why its QEMU exited.
